# 启动优化与图片打开速度

## 用户提供的 v1.0.16 板上日志

整机 `Startup time` 为 1.625 秒。SPL 读取 1,398,124 字节耗时 29,018 μs，报告 47,051 KB/s；LVDS framebuffer 在 1.371 秒分配，SDMC1 在 1.560 秒初始化。HMI 阶段标记从 `app_manager_init()` 开始计时：服务就绪 10 ms、UI 入口 30 ms、中文字体 47 ms、控件完成 131 ms、显示 flush 221 ms、LVGL render 224 ms。它们不包含 BootROM/SPL/Bootloader，不能与整机时间直接相加。

与用户先前提供的 v1.0.10 日志相比，整机启动时间从 1.627 秒到 1.625 秒，基本没有变化；HMI 的 flush/render 阶段从约 436/439 ms 降到 221/224 ms。当前主要耗时在 RT-Thread 应用标记之前，面板 framebuffer 在 1.371 秒才分配。QSPI 输入约 99 MHz、总线达到 99 MHz，SPL 读取速度约 47 MB/s。本轮不调整 NOR 时钟，也不改 BSP 显示或存储驱动。

## 新收到的 v1.0.18 热复位日志

该日志标记为 `Warm-Reset, reason: External-PIN-Reset`，`Startup time` 为 1.630 秒；SPL 读取 1,380,780 字节耗时 28,658 μs，速度 47,051 KB/s。LVDS framebuffer 在 1.374 秒分配，SDMC1 在 1.555 秒初始化。HMI 标记为 `app_services_ready=10 ms`、`hmi_ui_enter=30 ms`、`chinese_font_ready=46 ms`、`hmi_widgets_ready=129 ms`、`display_flush_return=219 ms`、`lvgl_render_ready=222 ms`。这些标记从 `app_manager_init()` 起算。

v1.0.16 的对照记录是 Power-On-Reset，Startup time 1.625 秒；复位条件不同，不能据此判断 v1.0.18 变慢。当前可见的大段耗时位于 RT-Thread HMI 阶段之前；NOR 读约 28.7 ms，不是主要瓶颈。此日志没有打开图片，因此不包含 `[image_preview]` 新增的分阶段耗时。

## 新收到的 v1.0.18 实机日志

最新日志为外部引脚热复位（`Reset action: Warm-Reset`），报告 `Startup time: 1.630 sec`。SPL 读取 1,380,780 字节耗时 28,658 μs，读取速度 47,051 KB/s；framebuffer 在 1.374 秒分配，SDMC1 在 1.555 秒初始化。HMI 标记为服务就绪 10 ms、UI 入口 30 ms、字体 46 ms、控件 129 ms、flush 219 ms、render 222 ms。QSPI 输入和总线仍约 99 MHz。

这份热复位日志与 v1.0.16 的上电复位日志不是同一复位条件，1.630 秒与 1.625 秒不能作为版本回归对比。它也没有图片打开过程，因此没有 `[image_preview]` 阶段耗时。SPL 读取减少约 17 KiB，在相同读取吞吐下只对应不到 1 ms 的理论差值；主要时间仍在显示 framebuffer 初始化前，且 HMI首帧标记另从 app_manager 起算。

## v1.0.20 实机启动日志（2026-11-02）

用户提供的日志显示 `Image version: 1.0.20`，复位条件为外部引脚热复位，整机 `Startup time` 为 **1.632 秒**。SPL 读取 1,389,240 字节耗时 28,834 μs，约 47,050 KB/s；LVDS framebuffer 在 1.375 秒分配，SDMC1 在 1.563 秒初始化。HMI 标记为服务就绪 10 ms、UI 入口 30 ms、字体 46 ms、控件 127 ms、flush 218 ms、render 221 ms。

此前 v1.0.18 同为外部引脚热复位，日志为 1.630 秒、framebuffer 1.374 秒、控件 129 ms、flush 219 ms、render 222 ms。当前两次测量只差 2 ms，应用阶段变化约 1–2 ms，**没有证据表明整机启动速度获得可测量的提升**；HMI 首帧约 221 ms 也不能代表上电到可操作的总时间。QSPI/NOR 配置未变。当前日志没有 `RT_DEBUG_INIT_CONFIG` 逐项输出，所以无法从它确定 1.375 秒前各初始化函数的具体耗时。

日志还显示 `/sdcard` 首次 FATFS 挂载失败，稍后才出现 `card insertion detected!`，但未包含后续挂载成功记录；需在页面确认 SD 是否最终可用。`/data` 的 LittleFS 挂载失败仍然存在；系统日志线程和升级状态文件使用 `/data/hmi.log`、`/data/upgrade.state`，因此持久化记录可能不可用，需要修复或确认数据分区文件系统。该日志没有工具箱连接、蜂鸣器动作或无线接口状态，不能用于验证这些功能。

## v1.0.21 静默 RT 配置与构建结果

正式 OS 配置在 `rt_hw_board_init()` 的驱动批量初始化前注册 `hmi_quiet` RT 设备并绑定控制台；串口写回调直接吞掉输出。生产配置同时关闭 RT UART0 驱动、FinSH/MSH 线程和 ULOG 输出，HMI 串口诊断格式化在正式配置下编译为空。v1.0.21 的 OtaProfile 仍保留 UART、FinSH 和 `RT_DEBUG_INIT`，用于后续临时逐项诊断。BootROM/SPL 使用独立输出路径，本次没有修改，因此其日志仍会显示。

SDK 成功构建 v1.0.21 工厂镜像：OS ITB 从 v1.0.20 的 1,392,640 字节降到 1,081,344 字节，RODATA 仍为 2,502,656 字节；完整 IMG 从 4,561,408 字节降到 4,250,112 字节。以 v1.0.20 日志中的 47,050 KB/s 估算，OS 读取量减少对应约 6–7 ms；这是按镜像大小推算，**不是 v1.0.21 的实机启动测量**。这轮优化移除了 RT UART 输出路径和 RT Shell 线程；仍需要同板、同复位条件测量才能确认总启动变化。

由于正式版本不再输出 RT-Thread 日志，整机启动时间不再能从该 UART 启动日志直接读取。需要 init 函数细分时，应使用保留串口输出的独立诊断 profile；静默正式版本的启动时长改用 GPIO 脉冲或外部计时。此次没有自动烧录、擦除 Flash 或修改 NOR 时钟。

## v1.0.22 图片预览与屏幕串口构建

v1.0.22 保留 `hmi_quiet` RT 控制台、FinSH/MSH 与 ULOG 静默配置，同时重新启用 UART0 驱动用于屏幕代号协议。UART0 收到 `CS000` 会报告当前 1024×600 LVDS/GT911 配置；收到 `CS001` 会返回 `NOT_CONFIGURED`。该协议应答不是 RT-Thread/HMI 日志。串口收发和上电耗时尚未在开发板验证。

图片预览改成原始像素 1:1：小图居中，大图按中心窗口裁切。BMP 解码器只按可视区域逐行读取并分配屏幕大小的 RGB565 输出缓冲；JPG/JPEG 与 PNG 通过 SDK MPP 已有裁剪命令设置源窗口和输出尺寸。JPEG/PNG 压缩输入仍限制为 4 MiB，PNG 像素数保留 SDK 800 万限制；JPEG 上限、MPP 硬件边界、CMA 余量和颜色结果需要板上验证。构建日志为 `stage_panel_serial_images_v1.0.22_build.log`，SDK 报告 `Luban-Lite is built successfully`，生成 4,262,400 字节工厂 IMG；该编译结果不代表实际显示验收。

## v1.0.23 UART RX、CS001 显示 profile

用户手动烧录 v1.0.22 后，串口助手以 115200/8N1 发送 `CS001` 未收到应答。v1.0.22 的 RX 工作线程丢弃了 UART 回调提供的字节数，改为请求固定 32 字节，可能无法及时消费短帧。v1.0.23 改为按回调字节数读取，并在 UART0 服务启动后输出当前 `READY` profile 行；该修复已编译，尚未板上验证。

CS001 将 `hmi_screen` 通过官方 ENV API 保存后软件重启。FAL 初始化移到 RT-Thread init 子优先级 2.9，早于 `aicfb_probe` 的设备初始化；panel overlay 在 probe 时读取 ENV，选择 EK79202DA 的 1280×800 timing descriptor。时序使用 72.4 MHz、总行 1440 DCLK、总帧 838 行；HSYNC 20、VSYNC 2 是落在 datasheet 允许范围内的工程选值，不是厂商给定的典型脉宽。该 profile 暂不启动触摸，启动行回报 `TOUCH=DISABLED`。LVDS strap、lane/polarity 和画面质量仍待目标板检查；可用串口发 `CS000` 回退。

## v1.0.18 软件改动

- 工厂和 OTA profile 关闭显式启用的 CMU、GPIO、DMA、CAN、Audio、GPAI、TSEN、PSADC 测试命令，减少固件内容；没有更改底层驱动时钟。
- 输入键盘延迟到首次聚焦文本框时创建，避免首页启动时构造整套隐藏键盘控件。
- 图片预览继续在独立工作线程中读取和解码；LVGL 线程用仅在预览期间运行的 20 ms 定时器显示结果，不再等待主界面 200 ms 状态轮询。
- 在工程 overlay 中优化官方 LVGL BMP 解码器：常见行对齐的倒序 BMP 一次顺序读取后原位翻转行序；行尾需补齐时按最多 32 KiB 批量读入。临时缓存分配失败时回退到逐行读取，保持低内存时的兼容路径。
- 增加图片文件头、MPP 解码、RGB565 归一化和总耗时日志，便于板上定位具体慢点。JPG/PNG 使用 SDK MPP 解码路径；不额外保留第二份完整帧缓存。
- QSPI/NOR、CPU、总线、A/B 健康确认、看门狗和签名校验均保持原设置。

SDK SCons 成功生成 v1.0.18 工厂镜像和 OTA 候选。OS ITB 为 1,384,448 字节，RODATA 为 2,502,656 字节；启用上述裁剪后，OS ELF text 段为 1,366,820 字节。包校验和 RSA 签名均通过主机侧检查。尚无同条件冷启动对照和图片打开计时，不能据此声称完整启动或图片加载速度已达到目标值。

## RT-Thread 初始化逐项诊断

v1.0.19 OtaProfile 启用 SDK RT_DEBUG_INIT_CONFIG：UART 输出每个 board/device/component/filesystem/app init 函数的耗时，并输出 rt_hw_board_init、timer_init、scheduler_init、application_thread_create 阶段汇总。profile 还细分 heap、memheap、sysclk、pinmux、board component 和 console 绑定。诊断固件额外打印会拉长启动，不用于评价正式版本总时间；请按每个 init 函数的 cost 排序，优先检查耗时最长且可延后的非必需初始化。

诊断包使用 OTA 升级后版本为 1.0.19，不能再退回 v1.0.18；之后的正式 OTA 需提高版本号。安装、串口采集和后续修复均由用户手动确认；本工程不会自动烧录或改动 NOR 时钟。
## 板上验收方法

1. 新板首次部署使用 v1.0.23 工厂镜像。该镜像含配套 SPL/Bootloader，烧录由用户手动执行。
2. v1.0.23 正式固件保持 RT 控制台静默；连续冷启动时记录 UART0 的 `CS000,READY`/`CS001,READY` 行，再以外部计时测量从电源沿到可操作界面，至少 10 次。
3. UART0 发送 `CS000`、`CS001` 和未知代号，确认当前 profile、重启切换与错误应答；在 CS001 下检查 1280×800 LVDS 画面。触摸当前关闭。
4. 检查热启动和连续快速打开/关闭图片时的内存占用、取消行为以及 SD 拔卡后的错误处理。

目标板上 v1.0.23 仍需 UART RX、启动 profile 行、CS001 LVDS、串口回退和同条件冷启动验收；A/B 升级和回滚也尚未验收。本轮没有使用 AiBurn、连接开发板或写入 Flash。上电进入 BROM 的问题由用户自行修复，本轮没有修改该启动路径。

构建记录：`stage42_ota_v1.0.18_build.log`、`stage43_factory_v1.0.18_build.log`。代码差异见 `v1.0.18_startup_image_optimization.patch`。
